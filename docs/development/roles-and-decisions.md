# roles-and-decisions.md — 役割分担と判断ポイント

> このプロジェクトのルールの土台。ほかのルール（`CLAUDE.md`、`.claude/rules/`、`AGENTS.md`）は、この文書の役割分担に合わせて書く。
> 関連 ADR：`docs/adr/ADR-0003-ai-led-development-roles.md`

## 前提

- **開発は基本的に AI エージェント（Claude Code、Codex など）に任せる**
- **Ryo は「何を作るか」と「それで良いか」を決める人**。コードを書く人ではない
  （開発・テスト・要件定義の経験があるので、気になればコードを見てよい。ただし必須にはしない）
- Ryo の作業時間は週 10〜15 時間。AI は Ryo の時間を「決めること」と「触って判断すること」に集中させる

---

## 1. 役割分担

| 領域 | Ryo（人間） | AI エージェント |
|---|---|---|
| 企画・世界観・キャラ・物語 | 採用するかを決める（決めたものが正典） | ブレスト、たたき台、調査、矛盾の指摘 |
| 仕様（何を作るか） | 完了条件を承認する（判断A） | 作るもの・完了条件・やらないことのたたき台 |
| 技術選定 | ADR を採択する（新しいツール・有料サービス・方針の変更） | 調査、比較、ADR の下書き。ADR の範囲内の細かい技術判断は自分で決めて記録する |
| 実装・テスト | — （見たければコードを見てよい） | 実装、テスト、リファクタ、デバッグ、動作確認 |
| 品質（客観） | — | テスト、自動 QC、検証の証拠をそろえる |
| 品質（主観） | **面白いか・可愛いか・世界観が伝わるか**を判断する（判断B） | 判断材料をそろえる（画面、動画、比較表、ツール名を隠した比較） |
| 画像などの素材 | 採用する素材を選ぶ。リリースに使うかを決める（ADR-0002） | 生成、自動 QC、生成ログ |
| お金 | 予算・上限・有料契約を決める | 費用の見積もり、上限の監視、超えそうなら止まって知らせる |
| 外部への公開 | SNS 投稿、ストア申請、課金設定、外部への共有を**自分の手で**行う | 素材と文面の準備まで |
| Git | コミット案の承認、push・マージの指示（判断C） | ブランチ作成、コミット案、マージの準備 |
| 記録 | 決める | 決定ログ（`docs/decisions.md`）、`PLAN.md`、各ドキュメントへの記録 |

## 2. 判断ポイント

### 定例（作業の流れの中で必ず通る）

| | いつ | AI が出すもの | Ryo が決めること |
|---|---|---|---|
| **判断A：着手** | 作り始める前 | 作るもの、完了条件（触って確かめられる言葉で）、やらないこと、おおよその手間・費用 | OK／直す／やめる |
| **判断B：確認** | できたとき | 動くもの（画面・動画・URL）、検証の結果、気になった点 | OK／直す／やめる |
| **判断C：取り込み** | 判断B の後 | コミット・マージの案（`docs/development/git-workflow.md`） | 承認、push の指示 |

- 判断A で OK が出たら、AI は**判断B まで止まらずに進める**（下の「止まる条件」に当たったときだけ止まる）
- 判断A は作るものの大きさに合わせて軽くしてよい。Phase 0 の試作なら、数行の提案に「OK」の一言で足りる
- 判断B では、コードの説明ではなく**触って・見て判断できる形**で出す
- テストコードそのものを Ryo が承認する手順はない。テストは判断A の完了条件から AI が作り、AI が自分で点検する

### 随時（AI が作業を止めて聞く条件）

次に当たったら、判断A の OK が出ていても**その場で止まって Ryo に聞く**。

1. **お金がかかる**：有料のサービス・契約、決められた上限を超えそうなとき
2. **外に出る**：公開、投稿、送信、外部への共有
3. **新しいものを入れる・方針を変える**：新しいツール・ライブラリ・サービス、ルールや方針の変更（→ ADR）
4. **取り消せない**：ファイルやデータの削除、Git 履歴の書き換え
5. **正典を変える**：決定済みの世界観・キャラ・物語・用語を変える
6. **権利・規約の判断**：ライセンス、商用利用、ストアの規約
7. **合意の範囲を超える**：判断A の範囲を超える、または完了条件を満たせないと分かった
8. **セキュリティのルールの例外**

### AI が止まらずに進めてよいこと（例）

- 調査、ブレスト、ドキュメント・ADR の下書き
- 判断A の後の実装、テスト、リファクタ、デバッグ
- ビルド、テストの実行、ローカルでの動作確認（アプリやページを立ち上げて触る、スクリーンショットを撮る）
- 決められた予算内での画像生成と自動 QC
- ブランチの作成（`lite` プロファイル）
- ADR の範囲内の細かい技術判断（理由を記録に残す）

## 3. AI から Ryo への報告のしかた

- **決めてほしいことを先頭に**書く。選択肢とおすすめを添える
- 「できた」「確認した」は、実行した結果（コマンドの出力、画面、動画）を添える
- 専門用語は短く補足する
- 判断に関係しない作業の細部は書かない

## 4. 決定の記録

- Ryo が決めたことは、**AI が `docs/decisions.md` に記録する**。日付・内容・どの場面で決まったかを書く
- 書くのは Ryo が明言したことだけ。AI の提案は書かない（提案は各ドキュメントに「案」として書く）
- 原案の決定ログ（`docs/original-docs/tsukumogami-game/docs/05_decisions.md`）は 2026-10-17 までの記録としてそのまま残す（読み取り専用）

## 5. テンプレートのゲート（Gate 0〜4）との対応

このリポジトリは Laravel の Web アプリ向けのテンプレートから始まった。ゲートは次のように置き換える。

| テンプレート | このプロジェクト |
|---|---|
| Gate 0（`docs/ai-context/` の記入） | 記入済み（2026-10-20） |
| Gate 1〜3（requirements / use-cases / data-model の承認） | **判断A に統合**。完了条件が仕様の役割を持つ。正式版（Phase 2 以降）で文書が必要になったら、そのとき ADR で再導入する |
| Gate 4（テストコードの人間による承認） | **廃止**。AI が完了条件からテストを作り、自分で点検する。Ryo は判断B で動作を見る |
| 「ユーザーから見える振る舞いの変更は人間の承認が必要」 | **残す**。判断A の範囲外の振る舞い変更は、止まる条件 7 に当たる |
