# ADR-0003: 開発を AI エージェント中心にし、ルールを「人間と AI の役割分担」に合わせて作り直す

## Status
Proposed（方針は 2026-10-20 Ryo 決定。役割分担と判断ポイントの中身は Ryo の確認待ち）

## Date
2026-10-20

## Context

- このリポジトリのルールは、Laravel + MySQL の Web アプリをチームで作るためのテンプレートだった。
  要件定義書・ユースケース・データモデルの承認（Gate 1〜3）、テストコードの人間による承認（Gate 4）を経てからコードを書く作り
- このプロジェクトはスマホゲームで、Phase 0 では画像生成のスクリプトとブラウザの試作ページを作る。
  テンプレートのゲートのままでは、use-cases.md が承認されるまでコードが書けない
- Ryo は個人開発（週 10〜15 時間）で、開発は基本的に AI エージェントに任せる方針（2026-10-20 決定）。
  Ryo の強みは「何を作るかを決める」「レビューして判断する」ことで、コードを書くことではない（原案の引き継ぎ資料）

## Decision

1. 人間（Ryo）と AI エージェントの役割分担、判断ポイント、AI が止まる条件を
   `docs/development/roles-and-decisions.md` に定義し、ルールの土台にする
2. 判断ポイントは3つに絞る：**判断A（着手：完了条件の承認）**、**判断B（確認：触って判断）**、**判断C（取り込み：コミット・マージ）**。
   加えて、お金・外部公開・新しいツール・取り消せない操作・正典の変更・権利・合意範囲の超過・セキュリティ例外では、AI がその場で止まって聞く
3. テンプレートの Gate 1〜3 は判断A に統合し、Gate 4（テストコードの人間による承認）は廃止する
4. Laravel・MySQL・Vue 専用のルール（`10-laravel.md`、`15-frontend.md`、`20-mysql.md`）は `meta/template-archive/` に退避する。
   書き換えたファイルの元の版も同じ場所に残す
5. Ryo の決定は AI が `docs/decisions.md` に記録する（原案の `05_decisions.md` は読み取り専用のまま残す）

## Rationale

- Ryo の時間を「決めること」「触って判断すること」に集中させるのが、個人開発の速度と品質の両方に効く
- テストコードの承認は、コードを読まない前提の人には負担が大きく、判断の質も上がりにくい。
  代わりに「完了条件」という平易な言葉で合意し、できたものを触って確かめる方が、Ryo の強みが活きる
- 止まる条件を明示することで、AI に任せる範囲を広げても、お金・公開・取り消せない操作では必ず人間が判断できる

### Rejected Alternatives
- **テンプレートのゲートをそのまま使う**：要件定義書・ユースケース・データモデルを先に書く必要があり、試作の速度に合わない
- **Phase 0 の試作コードだけゲートの対象外にする**：試作の後もルールと実態の食い違いが続く。役割分担から作り直す方が一度で済む

## Consequences

### Benefits
- Ryo が判断する場面が3つ＋止まる条件にまとまり、何を見ればよいかがはっきりする
- AI は判断A の後、止まる条件に当たらない限り進められる

### Drawbacks / Risks
- テストの中身を人間が見ないので、テストが的外れでも気づきにくい。
  → 完了条件から期待値を作ること、実装から期待値を写さないこと（`30-testing.md`）、判断B で実物を触ることで補う
- テンプレート由来のコマンド・フック・文書（`/review` の Laravel 向けの観点、`docs/architecture/` など）はまだ Laravel 前提のものが残る。
  使う場面が来たら、その都度このプロジェクト向けに直す（残りは `meta/template-archive/README.md` に一覧）
- 正式版（Phase 2 以降）で関わる人が増えたら、判断ポイントを見直す
